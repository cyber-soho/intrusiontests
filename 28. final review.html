Chapter 1

System Hacking: From Credentials to Cleanup (Days 16–18)

This chapter covers Phase 5 of the PTES framework — Post-Exploitation — and maps directly to the "System Hacking" module of the EC-Council CEH certification. The material is divided into four operational stages that follow the natural lifecycle of activity after an attacker gains initial access.

Lesson 1 — Credentials: Hashes and Cracking

The moment a penetration tester lands on a target system, the top priority is to locate and extract credentials. The IBM (International Business Machines) X-Force Threat Intelligence Index 2024 reported a 71 % year-over-year increase in attacks that relied on valid credentials — confirming that stealing passwords is often more effective than writing new exploits.

How operating systems store passwords. Modern systems store a mathematical fingerprint of each password rather than the password itself. That fingerprint is called a hash — the output of a one-way function that is fast to compute in the forward direction but practically impossible to reverse.

On Linux, password hashes live in the /etc/shadow file. A typical entry uses SHA-512 (Secure Hash Algorithm — 512-bit), indicated by the $6$ prefix. The hash also includes a random salt — additional data mixed in before hashing — which prevents precomputed rainbow table look-ups because every user's hash is unique even if two users choose the same password.

On Windows, passwords are stored as NTLM (NT LAN Manager) hashes inside the SAM (Security Account Manager) database. NTLM hashes are 32 hexadecimal characters long and are not salted, which makes them far faster to crack. A modern NVIDIA RTX 4090 GPU (Graphics Processing Unit) running Hashcat can test roughly 100 billion NTLM candidates per second.

Other hash types encountered in the field include MD5 (Message-Digest Algorithm 5) — 32 hex characters, cryptographically broken since 2004; SHA-1 (Secure Hash Algorithm 1) — 40 hex characters, deprecated but still found in legacy environments; bcrypt — deliberately slow, used by modern web applications; and NTLMv2 (NT LAN Manager Version 2) — a challenge-response protocol common in Active Directory (AD) networks.

The cracking workflow proceeds through five steps: obtain the hashes (dump /etc/shadow or extract SAM), identify the hash type (character-count analysis or tools such as hashid), choose an attack mode, run the cracking tool, and then analyse the results for password-reuse and lateral-movement opportunities.

Four attack modes dominate offensive practice. A dictionary attack tests every entry in a wordlist such as rockyou.txt — a collection of 14 million leaked passwords from the 2009 RockYou breach. A rule-based attack mutates dictionary words (capitalise the first letter, append digits, swap characters) to match real-world habits. A mask attack targets known password-policy patterns — for example, one uppercase letter followed by six lowercase letters and two digits. A brute-force attack tries every possible combination; it is guaranteed to succeed but impractical for long passwords.

The two primary cracking tools are Hashcat (GPU-accelerated, extremely fast) and John the Ripper (CPU-based, more flexible with exotic hash formats).

Lesson 2 — Local Privilege Escalation (LPE)

Initial access almost never lands the tester in a privileged context. The goal of LPE (Local Privilege Escalation) is to move from a standard user account to root (on Linux) or SYSTEM/Administrator (on Windows). The MITRE ATT&CK framework catalogues privilege escalation under Tactic TA0004.

Linux escalation vectors. (1) SUID (Set User ID) binaries — when a file's SUID bit is enabled, it runs with the owner's permissions (often root) regardless of who executes it; abusing a misconfigured SUID binary can spawn a root shell. The community-maintained GTFOBins catalogue lists exploitable SUID candidates. (2) Sudo misconfigurations — running sudo -l reveals commands the current user may execute as root; entries such as (ALL) NOPASSWD: /usr/bin/vim allow instant escalation because editors can launch subshells. (3) Cron-job abuse — if a scheduled task executes a world-writable script as root, injecting commands into that script grants root execution at the next trigger. (4) Kernel exploits — unpatched kernels with known CVE (Common Vulnerabilities and Exposures) entries can be exploited for direct root access. (5) Writable PATH hijacking — if a privileged script calls a binary by name without an absolute path and the attacker can write to a directory that appears earlier in the system PATH, placing a malicious binary there intercepts execution.

Enumeration tools: LinPEAS and WinPEAS automate the search for misconfigurations across both operating systems.

Windows escalation vectors. (1) Unquoted service paths — when a service binary path contains spaces and is not wrapped in quotation marks, Windows attempts alternative interpretations; an attacker who can write to one of those alternative locations hijacks the service. (2) Token impersonation / Potato attacks — services running as NETWORK SERVICE can impersonate higher-privilege tokens; the "Potato" family (Hot Potato, Sweet Potato, Juicy Potato, PrintSpoofer) abuses this mechanism to reach SYSTEM. (3) AlwaysInstallElevated — a Group Policy setting that, when enabled, causes every .msi (Microsoft Installer) package to install with SYSTEM privileges; the attacker can craft a malicious installer via msfvenom to escalate.

Lesson 3 — Persistence and Cleanup

Persistence is the practice of installing mechanisms that allow re-entry after reboots, credential rotations, or patch cycles. In a professional engagement it serves two purposes: maintaining reliable access for continued testing, and demonstrating to the client's incident-response team which footholds an attacker could establish.

Common Linux persistence techniques include crontab entries that execute a reverse-shell payload at fixed intervals and SSH (Secure Shell) authorised-key injection — placing the attacker's public key in a target user's ~/.ssh/authorized_keys file. Common Windows persistence techniques include Registry Run Keys (values under HKCU\Software\Microsoft\Windows\CurrentVersion\Run that execute a payload at every logon), Scheduled Tasks (triggered on logon, at a set time, or by a system event), and malicious Windows Services configured for automatic start.

Cleanup is non-negotiable. Every persistence mechanism — backdoors, registry entries, scheduled tasks, SSH keys — must be removed before the engagement ends. A persistence artefact left behind by a tester becomes a real attack surface for a malicious actor. The cleanup checklist also includes restoring file timestamps with touch (Linux) or timestomp (Windows) and clearing or truncating log entries the tester's activity generated.

Lesson 4 — OPSEC (Operations Security)

OPSEC governs everything from tool selection to evidence handling. Three attack surfaces expose a tester: the network footprint (every packet is evidence — DNS (Domain Name System) queries, HTTP traffic, SSH connections all leave traces), the disk footprint (uploaded tools, created files, and generated log entries), and the behavioural footprint (unusual activity patterns, such as running enumeration scripts at 3:00 AM, that trigger security monitoring).

Practical OPSEC rules per phase: during credential extraction, exfiltrate hashes over encrypted channels and wipe copies from disk; during privilege escalation, prefer living-off-the-land techniques that use built-in OS tools over uploading third-party binaries; during persistence, record every artefact in real time so nothing is missed during cleanup.

All activity is governed by the RoE (Rules of Engagement) — the legal document signed before the test begins, specifying scope, timing, evidence-handling procedures, and destruction policies.

Chapter 2

System Hacking 2: Sniffing, Spoofing, Malware & Endpoint Defence (Days 19–20)

This chapter extends the post-exploitation toolkit into network-layer attacks and introduces the defender's perspective through malware analysis fundamentals and EDR (Endpoint Detection and Response) technology.

Lesson 1 — Sniffing and MITM (Man-in-the-Middle) Attacks

Network sniffing — also called packet sniffing or protocol analysis — is the practice of capturing traffic as it traverses a network segment. Legitimate uses include troubleshooting and capacity planning; malicious uses focus on capturing credentials and sensitive data.

Passive versus active sniffing. Passive sniffing works on hub-based or wireless segments because hubs broadcast all traffic to every connected port; the attacker simply places their NIC (Network Interface Card) into promiscuous mode and reads everything. Active sniffing is required on switched networks because a switch maintains a MAC (Media Access Control) address table and delivers frames only to the correct port. Techniques for overcoming this include MAC flooding (overloading the switch table so it reverts to hub-like behaviour), ARP (Address Resolution Protocol) spoofing, and DNS spoofing.

Key tools: Wireshark (GUI-based, open-source protocol analyser), tcpdump (command-line sniffer for Linux/Unix), and Bettercap (active sniffing and MITM framework).

Lesson 2 — ARP Spoofing (ARP Cache Poisoning)

ARP bridges Layer 2 (data link) and Layer 3 (network) by mapping IP addresses to MAC addresses. When a device needs to reach an IP on the local segment it broadcasts an ARP request; the owner of that IP responds with its MAC address, and the result is cached. The critical weakness: ARP has no authentication mechanism — any device can send unsolicited ARP replies, and recipients accept them without verification. ARP was designed in 1982 under RFC 826 when network trust was assumed.

In an ARP spoofing attack, the attacker sends forged replies to both the victim and the gateway, claiming to be the other party. Both devices update their caches with the attacker's MAC. All subsequent traffic between victim and gateway now flows through the attacker's machine, enabling credential interception, session hijacking, and packet manipulation.

Defences: DAI (Dynamic ARP Inspection) on managed switches validates ARP packets against a trusted DHCP (Dynamic Host Configuration Protocol) snooping table; static ARP entries for critical infrastructure; 802.1X port-based access control.

Lesson 3 — PCAP (Packet Capture) Analysis

Every sniffer session can be saved as a PCAP file (using the libpcap format) or the newer PCAPNG format used by Wireshark by default. PCAP analysis turns raw captured data into actionable intelligence: credential extraction from HTTP POST requests, protocol anomaly identification, and evidence documentation.

Essential Wireshark display filters every tester should memorise: tcp.flags.syn == 1 && tcp.flags.ack == 0 (initial SYN packets indicating new connection attempts), http.request.method == "POST" (form submissions that may contain credentials), dns.qry.name contains "evil" (DNS queries to suspicious domains), and ip.addr == (isolate traffic to/from a specific host). The "Follow TCP Stream" feature reconstructs entire conversations from individual packets.

Lesson 4 — Malware Basics and Safety

Penetration testers need to understand malware for two reasons: offensive engagements often simulate malware delivery using benign payloads, and recognising malware communication patterns (C2 (Command-and-Control) beacons, data exfiltration channels) is essential during analysis.

Major malware categories. A virus attaches to legitimate files and replicates when the host file is executed. A worm self-replicates across networks without user interaction — WannaCry spread by exploiting a vulnerability in SMB (Server Message Block). A Trojan masquerades as legitimate software — Emotet began as a banking Trojan and evolved into a malware delivery platform. Ransomware encrypts files and demands payment — LockBit is among the most active families. A rootkit hides deep within the OS or firmware — the 2005 Sony BMG rootkit was secretly installed via music CDs. A RAT (Remote Access Trojan) gives the attacker full remote control — DarkComet is a widely studied example.

Delivery mechanisms include phishing emails, malicious downloads/drive-by-downloads, USB drop attacks (Stuxnet spread via infected USB drives to air-gapped systems), exploitation of software vulnerabilities, and social engineering.

Lab safety: always analyse suspected malware inside an isolated VM (Virtual Machine), snapshot before execution, disable shared folders and clipboard, and monitor network traffic for C2 callbacks.

Lesson 5 — Endpoint Detection and Response (EDR) Overview

Traditional antivirus relied on signature-based detection — matching files against a database of known malware patterns. Modern threats — zero-day exploits, fileless malware running entirely in memory, and living-off-the-land (LotL) techniques using legitimate OS binaries — bypass signatures routinely.

EDR addresses these gaps by monitoring endpoint behaviour rather than file identity. Four core capabilities define every EDR platform: (1) continuous monitoring and data collection via a lightweight agent that records process creation, file modifications, registry changes, network connections, and user logins; (2) threat detection through signatures, behavioural analytics, and machine-learning models; (3) investigation and threat hunting by SOC (Security Operations Centre) analysts using the collected telemetry; and (4) automated response — isolating a compromised endpoint, killing a malicious process, or rolling back file changes.

Chapter 3

Web Applications and APIs Hacking (Days 21–23)

Modern breaches concentrate on the application layer. This chapter covers the OWASP (Open Worldwide Application Security Project) Top 10, hands-on proxy tooling, input validation principles, and server-side request forgery.

Lesson 1 — OWASP Top 10 (SQLi, XSS, IDOR, Authentication Issues)

The OWASP Top 10 is a regularly updated awareness document ranking the most critical web application security risks. The 2025 edition ranks them as follows:

A01 — Broken Access Control (includes SSRF (Server-Side Request Forgery)); A02 — Security Misconfiguration; A03 — Software Supply Chain issues; A04 — Cryptographic Failures; A05 — Injection (includes SQLi (SQL Injection), XSS (Cross-Site Scripting), and command injection); A06 — Insecure Design; A07 — Authentication Failures; A08 — Software or Data Integrity Failures; A09 — Security Logging & Monitoring Failures; A10 — Insufficient Attack Protection.

SQL Injection (SQLi) occurs when user-supplied input is concatenated directly into an SQL query string without sanitisation. A malicious input such as ' OR 1=1 -- can bypass authentication, extract data, or modify records. The definitive defence is parameterised queries (also called prepared statements) — the database driver treats user input strictly as data, never as executable code.

Cross-Site Scripting (XSS) occurs when an application inserts untrusted data into a web page without escaping. The injected script runs in the victim's browser and can steal session cookies, redirect users, or deface pages. Three sub-types exist: Reflected XSS — the payload is part of the current request and immediately echoed in the response; Stored XSS — the payload is permanently saved on the server (e.g., in a database) and served to every user who views the affected page; and DOM-based (Document Object Model-based) XSS — the vulnerability exists entirely in client-side JavaScript that unsafely modifies the DOM.

IDOR (Insecure Direct Object Reference) is a broken-access-control flaw where the application exposes internal implementation objects — database IDs, filenames, or keys — in user-controllable parameters without verifying authorisation. Changing ?invoice=10042 to ?invoice=10043 in the URL bar grants access to another user's invoice if the server performs no ownership check.

Authentication Issues (OWASP A07) include transmitting credentials over unencrypted HTTP, exposing session identifiers in URLs, failing to invalidate session tokens on logout, missing or broken MFA (Multi-Factor Authentication), and allowing credential-stuffing attacks by not rate-limiting login attempts.

Lesson 2 — Burp Suite Basics

Burp Suite is the industry-standard intercepting proxy for web application testing. The Community Edition provides a manual proxy, Repeater (for re-sending modified requests), and Decoder (for encoding/decoding payloads). The Professional Edition adds an automated scanner and Intruder (for brute-forcing parameters, fuzzing fields, and enumerating IDOR vulnerabilities).

Workflow: configure the browser to route traffic through Burp's local proxy (default 127.0.0.1:8080), install Burp's CA (Certificate Authority) certificate so HTTPS interception works, then use the Proxy tab to intercept a request mid-flight, modify headers, cookies, or parameters, and forward the altered request to the server.

Lesson 3 — Input Validation

Input validation is the single most effective defence against injection-class vulnerabilities. The lesson distinguishes three levels: no validation (raw user input inserted directly — fully vulnerable), client-side-only validation (a JavaScript regex checks for dangerous characters, but is trivially bypassed by disabling JavaScript or modifying the request in Burp Suite), and full server-side validation using an allow-list regex that permits only known-safe characters and rejects everything else.

The key principle: never trust user input, regardless of source — form fields, URL parameters, cookies, HTTP headers, and API payloads are all attacker-controllable.

Lesson 4 — SSRF (Server-Side Request Forgery) Overview

SSRF occurs when an attacker tricks a server-side application into making HTTP requests to an unintended destination — typically internal resources that are inaccessible from the public internet: internal APIs (Application Programming Interfaces), admin panels, or cloud metadata endpoints.

The canonical cloud-exploitation scenario: a vulnerable URL-preview feature fetches http://169.254.169.254/latest/meta-data/ — the AWS (Amazon Web Services) EC2 (Elastic Compute Cloud) instance metadata endpoint — and returns IAM (Identity and Access Management) credentials that can grant full access to the cloud environment.

Defences include allow-listing outbound destinations, blocking requests to private IP ranges and link-local addresses (169.254.x.x), and validating URL schemes.

Chapter 4

Active Directory and Lateral Movement (Days 24–25)

Over 90 % of Fortune 1000 companies run Windows-centric networks governed by Active Directory (AD). Compromising one account rarely stays one account — attackers move laterally through trust relationships, ticket abuse, and hash reuse.

Lesson 1 — Kerberos Basics

Kerberos is the default authentication protocol in Active Directory environments. Three principals participate: the client (the user or service requesting access), the KDC (Key Distribution Center) (running on every Domain Controller, composed of the AS (Authentication Service) and the TGS (Ticket Granting Service)), and the target service.

The authentication exchange proceeds through six steps:

  1. AS-REQ (Authentication Service Request) — the client sends its username and a timestamp encrypted with its NTLM hash to the KDC.
  2. AS-REP (Authentication Service Response) — the KDC returns a TGT (Ticket Granting Ticket) encrypted with the KRBTGT (Kerberos Ticket Granting Ticket) account's hash, plus a session key.
  3. TGS-REQ (Ticket Granting Service Request) — the client presents its TGT and requests a ticket for a specific SPN (Service Principal Name).
  4. TGS-REP (Ticket Granting Service Response) — the KDC returns a Service Ticket encrypted with the target service account's NTLM hash.
  5. AP-REQ (Application Request) — the client presents the Service Ticket to the target service.
  6. AP-REP (Application Response) — the service optionally confirms its identity back to the client (mutual authentication).

    7. Each ticket contains a PAC (Privilege Attribute Certificate) listing the user's group memberships and privileges. An SPN (Service Principal Name) uniquely identifies each service instance.

    Why attackers target Kerberos: tickets are encrypted blobs that can be captured and cracked offline — the attacker never needs to contact the KDC again.

    Lesson 2 — AS-REP Roasting and Kerberoasting

    AS-REP Roasting targets accounts where Kerberos pre-authentication has been disabled. Normally, the client proves its identity by encrypting a timestamp with its NTLM hash during the AS-REQ. When pre-authentication is off, the KDC issues an AS-REP containing data encrypted with the target account's NTLM hash without any proof of identity. The attacker captures this blob and cracks it offline using Hashcat or John the Ripper.

    Attack chain: enumerate accounts with pre-auth disabled (using Impacket's GetNPUsers.py or Rubeus), send AS-REQ for each, receive AS-REP, extract the encrypted portion, and crack with a wordlist.

    Kerberoasting exploits the fact that any authenticated domain user can request a Service Ticket for any SPN. The returned TGS-REP is encrypted with the service account's NTLM hash. If the service account uses a weak password, the attacker cracks the ticket offline using GetUserSPNs.py from Impacket or Rubeus.

    Defences: enforce long, complex passwords (25+ characters) on service accounts; use gMSA (Group Managed Service Accounts) so AD auto-rotates passwords; monitor for high volumes of TGS requests from a single user.

    Lesson 3 — PTH (Pass-the-Hash) and Over-PTH (Over-Pass-the-Hash)

    When a user logs into a Windows machine, the LSASS (Local Security Authority Subsystem Service) process caches their NTLM hash in memory. An attacker with local administrator access can extract these hashes using Mimikatz (sekurlsa::logonpasswords) and then authenticate to other machines that accept the same credentials — without ever knowing the plaintext password. This is the Pass-the-Hash (PTH) attack.

    Tools for PTH execution include pth-winexe, Impacket's psexec.py, and CrackMapExec.

    Over-Pass-the-Hash (Over-PTH / Pass-the-Key) extends PTH into Kerberos-only environments. Rather than sending the NTLM hash directly, the attacker uses it to request a legitimate TGT from the KDC. All subsequent authentication uses standard Kerberos, making the attack harder to detect.

    Mimikatz command: sekurlsa::pth /user:admin /domain:corp.local /ntlm:

    Defences: deploy Credential Guard on Windows 10/11 endpoints to protect LSASS memory; monitor for logon events with Type 9 (NewCredentials) — a hallmark of PTH tools; disable NTLM where possible and enforce Kerberos with AES-256 encryption; use the Protected Users security group for privileged accounts.

    Lesson 4 — Graphing Attack Paths with BloodHound

    BloodHound is an open-source tool that maps Active Directory relationships — group memberships, local admin rights, session data, and ACLs (Access Control Lists) — into a Neo4j graph database. It then applies shortest-path algorithms to reveal attack chains that are invisible to manual analysis.

    Workflow: (1) Data collection — run SharpHound on a domain-joined machine to enumerate users, groups, computers, GPOs (Group Policy Objects), ACLs, and active sessions. (2) Ingestion — import the JSON output into BloodHound's Neo4j backend. (3) Querying — use built-in queries such as "Shortest Path to Domain Admin" or "Users with DCSync Rights."

    Key graph relationships: MemberOf (group membership), AdminTo (local admin rights on a computer), HasSession (active logon session), GenericAll (full control — reset passwords, modify ACLs), WriteDacl (can modify the DACL — Discretionary Access Control List), and DCSync (can replicate directory data and extract all password hashes).

    Lesson 5 — Lateral Movement Techniques

    Lateral movement is the post-exploitation phase where an attacker moves from the initial foothold to other systems within the network. Beyond PTH, common techniques include WMI (Windows Management Instrumentation) Execution (MITRE T1047), PSExec/SMB Exec (MITRE T1021.002), RDP (Remote Desktop Protocol) Hijacking (MITRE T1563.002), and DCOM (Distributed Component Object Model) execution (MITRE T1021.003).

    Delegation attacks. Constrained and unconstrained Kerberos delegation allow services to impersonate users to other services. Misconfigured delegation is a high-value escalation path.

    Defence-in-depth for AD: tiered administration (Domain Admins never log into standard workstations — Microsoft's Enterprise Access Model), LAPS (Local Administrator Password Solution) to randomise local admin passwords on every machine, Credential Guard, the Protected Users security group, and AES-256 enforcement for Kerberos.

Chapter 5

Perimeter Hacking (Days 26–27)

The perimeter — firewalls, IDS (Intrusion Detection System) appliances, and SOC analysts — is the last line of defence between the attacker and the internal network. This chapter covers evasion, deception, denial of service, and alert triage.

Lesson 1 — IDS/Firewall Evasion and Tunneling

A firewall filters traffic based on rules — source/destination IP, port, protocol, and (for application-layer firewalls) payload content. According to NIST (National Institute of Standards and Technology), firewalls fall into three broad categories: packet-filtering firewalls, stateful inspection firewalls, and application-level gateways (proxy firewalls).

An IDS monitors network or host activity and generates alerts. Two deployment types exist: NIDS (Network-based IDS) — tools such as Snort and Suricata monitor traffic on a network segment — and HIDS (Host-based IDS) — agents on individual machines monitor system calls, file integrity, and log entries. Detection approaches fall into signature-based detection (matching known attack patterns) and anomaly-based detection (flagging deviations from a learned baseline).

Evasion techniques exploit the fact that the IDS and the target host may process packets differently:

  • Packet fragmentation — splitting a malicious payload across multiple tiny fragments that individually do not match any IDS signature; in Nmap, the -f flag enables this.
  • Session splicing — delivering the payload in very small TCP (Transmission Control Protocol) segments to avoid signature matching.
  • TTL (Time To Live) manipulation — inserting decoy packets with TTL values calculated so the IDS sees them (and believes the connection is benign) but they expire before reaching the target.
  • Protocol-level encoding — transforming payloads into hex, Unicode, or URL-encoded forms that the target decodes but the IDS cannot match.
  • Decoy scanning — Nmap's -D option floods the target with scan packets appearing to originate from multiple decoy IP addresses, making the real attacker harder to identify.

Tunneling encapsulates one protocol inside another to bypass security controls: SSH tunneling (encrypted channel, supports local/remote/dynamic port forwarding), HTTP tunneling via tools like Chisel (traffic disguised as normal web browsing), DNS tunneling using Iodine or dnscat2 (data encoded in DNS query/response pairs), and ICMP (Internet Control Message Protocol) tunneling with tools like ptunnel (data hidden inside ping packets).

Lesson 2 — Service Misdirection

Service misdirection involves redirecting network services to unexpected destinations, deploying decoy services, and slowing down attackers.

Port redirection forwards traffic from one port to another, often on a different machine — a cornerstone of pivoting during post-exploitation. Banner manipulation changes the service identifier string returned during a connection; for instance, making an Apache web server report itself as Nginx to mislead attackers who rely on banner grabbing.

Honeypots are decoy systems intentionally designed to look like legitimate targets. Low-interaction honeypots such as Cowrie emulate SSH/Telnet and log every command an attacker types. High-interaction honeypots (honeynet architectures) simulate entire networks with databases, servers, and services. Binary Defense operates as both a honeypot and monitoring tool. The Honeynet Project is a leading research organisation developing open-source honeypot tools.

Tarpits deliberately slow down attackers. A TCP tarpit accepts incoming connections but responds extremely slowly, keeping the attacker's resources tied up. The LaBrea tool is a classic TCP tarpit implementation.

Lesson 3 — DoS (Denial of Service) Concepts and Ethics

A DoS (Denial of Service) attack aims to render a system or service unavailable to legitimate users.

DoS versus DDoS (Distributed Denial of Service). A DoS originates from a single source and is relatively easy to filter. A DDoS is launched from hundreds, thousands, or even millions of compromised devices (a botnet), making mitigation far more complex. Global DDoS attacks increased by over 100 % in 2024 compared to the previous year.

Three categories of DoS attacks: Volumetric attacks flood network bandwidth — UDP (User Datagram Protocol) floods and ICMP floods are common examples. Protocol attacks exploit weaknesses in network protocols — the SYN flood sends massive numbers of TCP SYN packets without completing the handshake, exhausting the server's connection table; amplification attacks (DNS amplification can produce a 70× amplification factor, NTP (Network Time Protocol) amplification, Memcached amplification) use reflectors to multiply attack traffic. Application-layer attacks target specific services — HTTP floods and Slowloris (holds connections open by sending partial requests) exhaust web server resources while consuming minimal attacker bandwidth.

Ethical constraints: penetration testers never launch DoS attacks without explicit written authorisation in the RoE. Even authorised testing is conducted in isolated environments or during maintenance windows. The goal is to assess resilience, not to cause damage.

Lesson 4 — Log and Alert Triage

Logs are time-stamped records of events. Common formats include Syslog (Linux/Unix and network devices), WEL (Windows Event Log), and CEF (Common Event Format) designed for SIEM (Security Information and Event Management) interoperability.

A SIEM is the nerve centre of a SOC. It collects logs from every device, normalises them into a consistent format, correlates events across multiple sources, and generates prioritised alerts. Major platforms include Splunk, IBM QRadar, Microsoft Sentinel, and the open-source Elastic Security (ELK Stack).

The triage process follows four steps: (1) Initial Assessment — review the alert's source, severity, and detection-rule fidelity; (2) Entity Enrichment — gather context using threat intelligence from MITRE ATT&CK, AlienVault OTX (Open Threat Exchange), and VirusTotal; (3) Verdict — classify as True Positive (real attack), False Positive (benign event matching a rule), True Negative, or False Negative (missed real attack); (4) Escalation or Closure — true positives go to incident response; false positives trigger rule tuning.

Alert fatigue is the greatest operational threat to SOC effectiveness. When analysts face hundreds of false positives per shift, they begin dismissing alerts without proper investigation — creating openings for real attacks. Solutions include continuous rule tuning, SOAR (Security Orchestration, Automation, and Response) platforms for automating repetitive triage steps, and UEBA (User and Entity Behaviour Analytics) for baseline-deviation detection.

Part B

Scenario-Based Case Studies

Case Study 1

The Unsalted Hash Disaster

Chapter 1, Lesson 1 (Credentials — Hashes and Cracking)

Scenario: During a penetration test of a mid-size insurance company, your team gains low-privilege access to a Windows Server 2016 file server. You extract the local SAM (Security Account Manager) database using a tool such as reg save and discover that 15 local accounts store their passwords as NTLM (NT LAN Manager) hashes. Using Hashcat with the rockyou.txt wordlist and a single RTX 4090 GPU (Graphics Processing Unit), your team cracks 12 of the 15 passwords within four minutes. Seven of those cracked passwords are reused across the Active Directory (AD) domain, granting access to two additional servers and a shared drive containing unencrypted customer records.

Question: Why were NTLM hashes cracked so quickly, and what organisational controls would have prevented this cascade?

Most Probable Answer

NTLM hashes lack salting — the same password always produces the same hash — and the algorithm is computationally trivial, allowing modern GPUs to test approximately 100 billion candidates per second. Twelve of fifteen accounts fell because employees chose passwords present in a common breach wordlist, indicating the absence of a meaningful password-complexity policy and no blacklist of known-compromised passwords. The cascade across the domain happened because password reuse was not detected or prevented. Organisational controls that would have stopped or limited the damage include enforcing a minimum 14-character password policy, implementing a compromised-password blacklist (Azure AD Password Protection, for example), disabling legacy NTLM authentication in favour of Kerberos with AES-256 encryption, deploying MFA (Multi-Factor Authentication) for all administrative access, and using LAPS (Local Administrator Password Solution) to ensure every machine has a unique local administrator password.

Case Study 2

The Forgotten Cron Job

Chapter 1, Lessons 2 and 3 (Privilege Escalation; Persistence and Cleanup)

Scenario: A junior tester on your team establishes persistence on a compromised Ubuntu web server by adding a crontab entry that executes a reverse shell every five minutes. The engagement concludes on Friday afternoon. On Monday, the client's SOC (Security Operations Centre) contacts you in a panic — their SIEM (Security Information and Event Management) flagged repetitive outbound connections from the web server to an IP address that belongs to your team's VPN (Virtual Private Network) exit node. The cron job was never removed.

Question: What went wrong, and what procedural safeguards should be in place?

Most Probable Answer

The tester failed the cleanup phase. Every persistence mechanism — backdoors, registry entries, crontab lines, SSH keys, scheduled tasks — must be catalogued in real time during installation so that nothing is missed during removal. Procedural safeguards include maintaining a live artefact log (a shared document that every team member updates immediately upon creating any persistence mechanism), running a post-engagement cleanup checklist verified by a second team member, re-scanning the target environment with the same enumeration tools used during testing to confirm no residual artefacts exist, and including explicit cleanup verification in the final report sign-off process. Under the RoE (Rules of Engagement), any tester artefact left behind transforms from a controlled test mechanism into a genuine security vulnerability — and the testing firm bears responsibility.

Case Study 3

The Poisoned ARP Cache

Case Study 5

Case Study 8

Tunneling Past the IDS

Most Probable Answer

Case Study 10

Alert Fatigue Lets an Attacker Slip Through

Chapter 5, Lesson 4 (Log and Alert Triage)

Scenario: A retail company's SOC (Security Operations Centre) runs Splunk as its SIEM. The IDS generates approximately 4,200 alerts per day, of which 96 % are false positives caused by poorly tuned detection rules. Over three weeks, a real attacker conducts low-and-slow reconnaissance — one port scan every 90 minutes, each from a different source IP — and eventually exploits a known vulnerability in an unpatched Apache Struts server. The exploitation alert fires as a "Medium" severity event, but the on-duty analyst dismisses it along with a batch of 300 other medium-severity alerts at the end of their shift. The attacker establishes persistence and exfiltrates 2.3 million customer records over the following ten days.

Question: Where did the detection-and-response pipeline fail, and how should the SOC be restructured?

Most Probable Answer

The 96 % false-positive rate caused severe alert fatigue — analysts were effectively trained to ignore alerts rather than investigate them. The slow reconnaissance activity evaded rate-based detection thresholds because each scan came from a different IP and was spaced 90 minutes apart. When the actual exploitation alert fired, it was drowned in noise and dismissed without enrichment or investigation. Restructuring should address several layers: (1) undertake an aggressive detection-rule tuning campaign — disable or rewrite the rules responsible for the highest false-positive volumes, and implement a feedback loop where every false positive triggers a tuning ticket; (2) deploy a SOAR (Security Orchestration, Automation, and Response) platform to automate repetitive enrichment steps (IP reputation look-up, asset criticality tagging, user-behaviour baseline comparison) so analysts focus on decision-making rather than data gathering; (3) implement UEBA (User and Entity Behaviour Analytics) to detect distributed low-and-slow reconnaissance that individual signature rules miss; (4) create a critical-asset watchlist — any alert involving the Apache Struts server (a known high-risk asset) should be automatically escalated to "High" severity regardless of the default rule classification; and (5) establish a patch-management SLA (Service Level Agreement) for internet-facing systems, ensuring known vulnerabilities are remediated within a defined timeframe.

Chapter 1, Lesson 1 — Credentials
1. Explain why NTLM (NT LAN Manager) hashes are significantly easier to crack than SHA-512 hashes used on Linux systems. In your answer, discuss the role of salting and computational cost.
💡 Hint

Compare the two algorithms on three axes — salt usage, computational speed, and the resulting implications for offline cracking.

✓ Answer

NTLM hashes are fast to compute and lack salting. Because there is no random salt appended before hashing, two users who choose the same password produce the same NTLM hash — making precomputed rainbow-table lookups effective. The NTLM algorithm itself is computationally trivial (a single MD4 operation), allowing modern GPUs to test roughly 100 billion candidates per second. In contrast, SHA-512 hashes in Linux's /etc/shadow incorporate a unique random salt per user and typically apply multiple rounds of the hash function ($6$rounds=5000$), dramatically increasing the per-guess cost. Even if two Linux users share the same password, their hashes differ because of the salt. The combined effect is that a password that survives hours of attack against SHA-512 can fall in seconds against NTLM. This is why modern best practices recommend disabling legacy NTLM authentication and enforcing Kerberos with AES-256 in Active Directory environments.

Chapter 1, Lesson 2 — Privilege Escalation
2. Describe the general methodology a penetration tester follows when attempting local privilege escalation on a Linux system, including at least three specific vectors.
💡 Hint

Begin with enumeration (automated and manual), then list specific misconfigurations or weaknesses that lead to root.

✓ Answer

The methodology begins with automated enumeration using tools such as LinPEAS, which scans for misconfigurations, outdated software, and insecure permissions. The tester then investigates specific vectors. First, SUID binary abuse — the tester searches for binaries with the SUID bit set (find / -perm -4000) and cross-references them against GTFOBins to identify those that can spawn a root shell. Second, sudo misconfigurations — sudo -l reveals commands executable as root; entries like NOPASSWD: /usr/bin/vim allow shell escapes within the editor. Third, cron-job exploitation — if a scheduled task runs a world-writable script as root, injecting commands into that script grants root execution on the next trigger. Additional vectors include kernel exploits against unpatched kernels with known CVEs, writable PATH hijacking when privileged scripts call binaries by name without absolute paths, and exploiting misconfigured capabilities (e.g., Python with cap_setuid). Each finding is documented with evidence for the final report.

Chapter 2, Lessons 1 & 2 — ARP Spoofing and Defences
4. Explain how an ARP (Address Resolution Protocol) spoofing attack works at the protocol level, and recommend at least two network-level defences.
💡 Hint

Start with how ARP resolves IP-to-MAC mappings, explain the lack of authentication, and describe how the attacker inserts themselves between victim and gateway.

✓ Answer

ARP operates at Layer 2, resolving IP addresses to MAC addresses. When a device needs to communicate, it broadcasts an ARP request; the owner of the target IP responds with its MAC address, which is cached. Because ARP includes no authentication (as designed in RFC 826), any device can send unsolicited replies. In an ARP spoofing attack, the attacker sends forged ARP replies to the victim (claiming the attacker's MAC is the gateway's IP) and to the gateway (claiming the attacker's MAC is the victim's IP). Both update their caches, routing all traffic through the attacker — creating a Man-in-the-Middle position. Defences include DAI (Dynamic ARP Inspection), which validates ARP packets against the DHCP snooping binding table on managed switches, rejecting replies that do not match known IP-to-MAC bindings; 802.1X port-based access control, which authenticates every device before granting network access; and static ARP entries for critical infrastructure such as the default gateway and domain controllers.

Chapter 2, Lessons 4 & 5 — Malware and EDR
5. Compare traditional signature-based antivirus with modern EDR (Endpoint Detection and Response). Identify at least two threat categories that bypass signatures and explain how EDR addresses them.
💡 Hint

Consider zero-day exploits, fileless malware, and living-off-the-land techniques.

✓ Answer

Traditional antivirus matches files against a database of known malware signatures — if a file's hash or byte pattern matches, it is flagged. This approach fails against zero-day exploits (malware using previously unknown vulnerabilities for which no signature exists) and fileless malware (attacks that execute entirely in memory without dropping a file to disk — PowerShell-based attacks, for example). Living-off-the-land (LotL) techniques use legitimate OS tools (cmd.exe, PowerShell, certutil) for malicious purposes; since the binaries are signed and trusted, signatures do not flag them. EDR addresses these gaps by shifting from file identity to behavioural monitoring. A lightweight agent on each endpoint collects telemetry — process creation, parent-child process relationships, registry modifications, network connections — and sends it to a central analytics platform. If PowerShell spawns a child process that makes an outbound connection to an unfamiliar domain, EDR detects the suspicious behaviour chain regardless of whether any file matches a known signature. Automated response capabilities allow EDR to isolate the endpoint or kill the process in real time.

Chapter 3, Lesson 1 — SQL Injection
6. Describe the mechanics of an SQL Injection (SQLi) attack, explain why concatenating user input into SQL queries is dangerous, and outline the primary defence.
💡 Hint

Walk through a concrete example of a vulnerable login query and show how ' OR 1=1 -- alters the query logic.

✓ Answer

SQL Injection occurs when an application builds SQL queries by directly concatenating user-supplied input. Consider a login query: SELECT FROM users WHERE username = ' + input + ' AND password = ' + input + '. If the attacker submits ' OR 1=1 -- as the username, the resulting query becomes SELECT FROM users WHERE username = '' OR 1=1 --' AND password = ''. The OR 1=1 condition is always true, and -- comments out the password check, so the query returns all rows and the attacker is authenticated without valid credentials. This works because the database cannot distinguish between the developer's intended SQL structure and the attacker's injected logic. The primary defence is parameterised queries (prepared statements), where the SQL structure is defined first with placeholder markers, and user input is bound as data parameters. The database engine treats the input strictly as literal values, making it structurally impossible for injected SQL fragments to alter the query logic.

Chapter 3, Lesson 4 — SSRF
7. Explain the concept of SSRF (Server-Side Request Forgery) and describe a realistic cloud-based exploitation scenario. Include at least two defensive measures.
💡 Hint

Focus on how a vulnerable server-side feature can be abused to reach internal resources that are not exposed to the internet.

✓ Answer

SSRF occurs when an attacker manipulates a server-side application into making HTTP requests to an unintended destination — typically internal resources that the attacker cannot reach directly from the internet. In a cloud-based scenario, consider a SaaS application running on AWS EC2 that includes a "URL Preview" feature. The attacker submits http://169.254.169.254/latest/meta-data/iam/security-credentials/ as the preview URL. The application server, running inside the AWS environment, contacts the EC2 instance metadata endpoint and returns temporary IAM credentials in the response. These credentials may grant access to S3 buckets, databases, or other AWS services. Defensive measures include: implementing an allow-list of permitted outbound domains for any server-side HTTP-fetch feature; blocking all requests to RFC 1918 private IP ranges and the 169.254.x.x link-local range; upgrading to IMDSv2, which requires a session token obtained via a PUT request that SSRF payloads typically cannot perform; and applying least-privilege IAM roles to EC2 instances so that leaked credentials minimise blast radius.

ESSAY
Chapter 4, Lesson 1 — Kerberos
8. Outline the six steps of the Kerberos authentication exchange in an Active Directory environment, and explain why attackers target this protocol.
💡 Hint

Walk through AS-REQ → AS-REP → TGS-REQ → TGS-REP → AP-REQ → AP-REP, and note which keys encrypt which tickets.

✓ Answer

Step 1 (AS-REQ): the client sends its username and a timestamp encrypted with its NTLM hash to the KDC. Step 2 (AS-REP): the KDC returns a TGT encrypted with the KRBTGT account's hash, plus a session key encrypted with the client's hash. Step 3 (TGS-REQ): the client presents its TGT and requests a Service Ticket for a specific SPN. Step 4 (TGS-REP): the KDC returns a Service Ticket encrypted with the target service account's NTLM hash. Step 5 (AP-REQ): the client presents the Service Ticket to the target service. Step 6 (AP-REP): the service optionally confirms its identity back to the client. Attackers target Kerberos because tickets are encrypted blobs that can be captured and cracked offline — without ever contacting the KDC again. If an attacker obtains the KRBTGT hash, they can forge TGTs for any user (Golden Ticket attack). If they crack a Service Ticket, they learn the service account's password (Kerberoasting). The protocol's reliance on symmetric encryption means that possessing the right hash grants unlimited replay and forging capability.

Chapter 4, Lesson 2 — AS-REP Roasting vs. Kerberoasting
9. Compare and contrast AS-REP Roasting and Kerberoasting. For each, state the precondition, the attack mechanism, and one specific defence.
💡 Hint

Both are offline cracking attacks against Kerberos, but they target different parts of the authentication exchange and require different preconditions.

✓ Answer

AS-REP Roasting targets accounts with Kerberos pre-authentication disabled. The attacker sends an AS-REQ for such an account, and the KDC responds with an AS-REP encrypted using the account's NTLM hash — without requiring proof of identity. The attacker captures this blob and cracks it offline. Defence: ensure pre-authentication is enabled for all accounts and audit Active Directory for exceptions. Kerberoasting targets any user account with a registered SPN. Any authenticated domain user can request a TGS ticket for any SPN. The returned Service Ticket is encrypted with the service account's NTLM hash. If the service account uses a weak password, the ticket is crackable offline. Defence: migrate service accounts to gMSA (Group Managed Service Accounts), which use 120-character auto-rotated passwords that are effectively uncrackable. The key distinction is the precondition: AS-REP Roasting requires a specific misconfiguration (pre-auth disabled), while Kerberoasting exploits a design feature of the protocol (any user can request any TGS) and depends entirely on password strength for resistance.

Chapter 4, Lessons 3 & 5 — PTH and Lateral Movement
10. Describe the Pass-the-Hash (PTH) technique and explain how it enables lateral movement across a Windows network. Recommend at least two defensive measures.
💡 Hint

Start from credential extraction via Mimikatz, trace the hash to authentication on remote machines, and connect to the broader concept of lateral movement.

✓ Answer

When a user authenticates to a Windows machine, LSASS caches their NTLM hash in memory. An attacker with local administrator access runs Mimikatz (sekurlsa::logonpasswords) to extract these hashes. The attacker then uses the stolen hash to authenticate to other machines on the network — the NTLM protocol accepts the hash directly without requiring the plaintext password. Tools like CrackMapExec can spray a single hash across an entire subnet, identifying every machine that accepts it. If the compromised account has local admin rights on other machines (common when organisations reuse local admin passwords), each successful authentication opens another pivot point for further credential extraction and deeper network penetration. This chain reaction is what makes PTH one of the most powerful lateral movement techniques. Defensive measures include deploying LAPS so each machine has a unique local admin password (breaking the spray chain), enabling Credential Guard to protect LSASS memory from being dumped, monitoring for logon events with Type 9 (NewCredentials) which indicates PTH tool usage, and enforcing tiered administration so privileged credentials are never exposed on lower-tier machines.

Chapter 4, Lesson 4 — BloodHound
11. Explain how BloodHound aids penetration testers in identifying attack paths through Active Directory. Describe the data-collection, ingestion, and query phases.
💡 Hint

Focus on how graph theory reveals chains of permissions that are invisible to manual analysis.

✓ Answer

BloodHound transforms complex Active Directory permission structures into a visual graph that reveals attack paths invisible to manual enumeration. In the data-collection phase, the tester runs SharpHound on a domain-joined machine to enumerate users, groups, computers, GPOs, ACLs, and active logon sessions, producing JSON output files. In the ingestion phase, this JSON data is imported into BloodHound's Neo4j graph database, where each AD object becomes a node and each relationship (MemberOf, AdminTo, HasSession, GenericAll, WriteDacl, DCSync) becomes an edge. In the query phase, the tester uses built-in queries — "Shortest Path to Domain Admin," "Users with DCSync Rights," "Kerberoastable Accounts" — or writes custom Cypher queries to identify specific attack chains. BloodHound then applies shortest-path algorithms across the graph, revealing multi-hop escalation routes — for example, User A → HasSession on Workstation B → AdminTo Server C → GenericAll on Group D → MemberOf Domain Admins. These chains are often four or five hops long and span organisational boundaries that no single administrator would notice.

Chapter 5, Lesson 1 — IDS Evasion and Tunneling
12. Explain two IDS (Intrusion Detection System) evasion techniques and two tunneling methods a penetration tester might use to bypass perimeter defences. For each, describe how it works and why it is effective.
💡 Hint

Choose one packet-level evasion and one scanning evasion; choose one common tunneling protocol and one that exploits rarely-blocked traffic.

✓ Answer

Packet fragmentation splits a malicious payload across multiple tiny IP fragments (Nmap's -f flag). Because many IDS devices skip or poorly perform fragment reassembly due to the CPU cost, no individual fragment matches a detection signature — the attack passes undetected while the target host reassembles and processes the complete payload. Decoy scanning (Nmap -D) sends identical probe packets appearing to originate from multiple spoofed IP addresses alongside the real scan; the IDS sees scan traffic from many sources simultaneously and cannot easily distinguish the attacker's true address from the decoys. For tunneling, SSH tunneling creates an encrypted channel that can carry any TCP protocol through local, remote, or dynamic port forwarding — a firewall that allows outbound SSH on port 22 unknowingly permits the tester to route any internal traffic through the tunnel. DNS tunneling (via Iodine or dnscat2) encodes data inside DNS query-and-response pairs; because DNS traffic is essential for network operation and rarely blocked, the tunnel passes through most firewalls without triggering alerts, making it particularly effective for data exfiltration from restricted environments.

Chapter 5, Lesson 2 — Service Misdirection
13. Define honeypots and tarpits, explain their roles in defensive security, and give one example tool for each.
💡 Hint

Both are deception technologies, but they serve different purposes — one gathers intelligence, the other wastes attacker resources.

✓ Answer

A honeypot is a decoy system intentionally designed to resemble a legitimate production target. Its purpose is to attract attackers, observe their techniques, and collect intelligence — commands entered, tools uploaded, lateral movement attempts — without exposing real assets. Cowrie is a widely deployed medium-interaction SSH/Telnet honeypot that emulates a shell environment and logs every command. Honeypots are valuable because they generate high-fidelity alerts: any interaction with a system that has no legitimate users is inherently suspicious, producing virtually zero false positives. A tarpit, by contrast, is designed to waste attacker resources. A TCP tarpit accepts incoming connections but responds extremely slowly — acknowledging the TCP handshake, then drip-feeding data at minimal speed, keeping the attacker's socket and scanning threads tied up indefinitely. LaBrea is a classic TCP tarpit tool that creates "sticky" connections on unused IP space. While honeypots focus on intelligence gathering and detection, tarpits focus on resource denial — slowing down port scans, worm propagation, and brute-force attempts. Together, they form a complementary deception layer within a defence-in-depth architecture.

Chapter 5, Lesson 3 — DoS
14. Differentiate between volumetric, protocol, and application-layer DoS (Denial of Service) attacks. Provide one example of each and explain the ethical constraints on DoS testing.
💡 Hint

Each category targets a different resource — bandwidth, protocol state tables, or application logic.

✓ Answer

Volumetric attacks flood the target's network bandwidth with enormous traffic volumes. A UDP flood, for example, sends massive numbers of UDP packets to random ports on the target, overwhelming its ability to process legitimate traffic. Protocol attacks exploit weaknesses in network protocol implementations. The SYN flood sends thousands of TCP SYN packets without completing the three-way handshake, filling the server's connection state table with half-open connections and preventing legitimate users from connecting. Application-layer attacks target specific services with requests that appear normal but exhaust server resources. Slowloris holds HTTP connections open by sending partial request headers that are never completed, consuming all available web server connection slots while using minimal attacker bandwidth. Ethical constraints require that DoS testing is performed only with explicit written authorisation in the RoE, targeting only the specified systems (typically staging environments, not production), during agreed maintenance windows, and with a live communication channel to the client's operations team. An accidental hit against the wrong target or at the wrong time can cause significant financial and reputational damage — making procedural rigour essential.

Chapter 5, Lesson 4 — Log Triage and Alert Fatigue
15. Explain the SOC (Security Operations Centre) alert triage process and discuss why alert fatigue is considered the greatest operational threat. Propose at least two solutions.
💡 Hint

Walk through the four triage steps, then explain the psychological and operational impact of a high false-positive rate.

✓ Answer

When an alert appears on a SOC analyst's dashboard, they follow a structured four-step triage process. First, Initial Assessment — the analyst reviews the alert's source, severity level, and the fidelity of the detection rule that generated it. Second, Entity Enrichment — the analyst gathers context: the affected user's normal behaviour, the criticality of the targeted asset, and whether the source IP appears in threat intelligence feeds from providers such as MITRE ATT&CK, AlienVault OTX, or VirusTotal. Third, Verdict — the analyst classifies the event as a True Positive, False Positive, True Negative, or False Negative. Fourth, Escalation or Closure — true positives are escalated to incident response; false positives are documented and the triggering rule is tuned. Alert fatigue arises when the false-positive rate is so high that analysts begin dismissing alerts without proper investigation — the sheer volume overwhelms their capacity for careful analysis. This is the single most dangerous operational failure because real attacks can hide among thousands of false alarms. Solutions include aggressive detection-rule tuning (rewrite or disable the noisiest rules and establish a feedback loop), deploying SOAR platforms to automate repetitive enrichment steps (IP look-ups, asset tagging, baseline comparisons), and implementing UEBA to detect subtle anomalies that pattern-matching rules miss.
